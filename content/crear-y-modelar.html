Crear una base con intención

Una base de datos se crea una vez, pero su codificación y colación afectan cada texto que guardes. Para español y datos de personas, utf8mb4 evita problemas con acentos, emojis y caracteres fuera del plano básico.

DROP DATABASE IF EXISTS banco_sangre;
CREATE DATABASE banco_sangre
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_spanish_ci;

USE banco_sangre;

utf8mb4 es el conjunto de caracteres; utf8mb4_spanish_ci define cómo se comparan y ordenan los textos (ci = case insensitive). Si comparas correos, quizá quieras una colación binaria o normalizar a minúsculas antes de guardar.

PRIMARY KEY, FOREIGN KEY y el resto

  • PRIMARY KEY: identifica de forma única cada fila. No admite NULL y suele ser autoincremental.
  • FOREIGN KEY: obliga a que el valor exista en otra tabla. Es la diferencia entre una base relacional y una colección de archivos.
  • UNIQUE: impide duplicados; permite NULL (una vez en MySQL).
  • NOT NULL: el dato es obligatorio.
  • CHECK: valida una condición; MySQL 8 la aplica de verdad.
  • DEFAULT: valor cuando no se envía ninguno.
CREATE TABLE donantes (
  id_donante       INT AUTO_INCREMENT PRIMARY KEY,
  nombre           VARCHAR(60) NOT NULL,
  apellido_paterno VARCHAR(60) NOT NULL,
  fecha_nacimiento DATE NOT NULL,
  tipo_sangre      ENUM('A','B','AB','O') NOT NULL,
  factor_rh        ENUM('+','-') NOT NULL,
  correo           VARCHAR(120) UNIQUE,
  activo           TINYINT NOT NULL DEFAULT 1,
  CONSTRAINT chk_nacimiento CHECK (fecha_nacimiento >= '1900-01-01')
) ENGINE=InnoDB;

Cuidado con CURRENT_DATE

MySQL 8 no permite funciones no deterministas como CURRENT_DATE dentro de un CHECK. La regla «la fecha no puede ser futura» se valida en la aplicación o con un trigger; el CHECK solo comprueba un límite fijo.

La tabla anterior no guarda la donación: guarda a la persona. La donación es otro hecho, con su propia fecha, peso, hemoglobina y estado. Separar hechos evita repetir datos y permite que una persona done muchas veces.

CREATE TABLE donaciones (
  id_donacion    INT AUTO_INCREMENT PRIMARY KEY,
  id_donante     INT NOT NULL,
  fecha_donacion DATETIME NOT NULL,
  tipo_donacion  ENUM('voluntaria','reposicion','autologa') NOT NULL DEFAULT 'voluntaria',
  peso_kg        DECIMAL(5,2),
  hemoglobina    DECIMAL(4,2),
  estado         ENUM('registrada','apta','rechazada') NOT NULL DEFAULT 'registrada',
  CONSTRAINT fk_donacion_donante
    FOREIGN KEY (id_donante) REFERENCES donantes (id_donante)
    ON UPDATE CASCADE ON DELETE RESTRICT,
  CONSTRAINT chk_peso CHECK (peso_kg IS NULL OR peso_kg > 0)
) ENGINE=InnoDB;

ON DELETE RESTRICT

Si alguien intenta borrar un donante con donaciones registradas, MySQL lo impide. En un banco de sangre eso es correcto: la trazabilidad no se borra. Si quisieras borrado en cascada, lo pensarías dos veces antes de aplicarlo a datos clínicos.

La integridad no es un lujo

Sin FOREIGN KEY, nada impide registrar una unidad con id_donacion = 999 que no existe. La aplicación podría validarlo, pero cualquier script, importación o error humano puede saltarse esa validación. La base de datos es el último guardián.

Caso banco de sangre

El esquema del proyecto tiene 12 tablas. La más importante no es la más grande: es unidades_sangre, porque conecta donación, pruebas, solicitudes y despachos. Su codigo_barras es único y su estado solo puede ser uno de cinco valores.

Cambiar un esquema sin romperlo

-- Agregar una columna opcional
ALTER TABLE donantes
  ADD COLUMN notas_internas VARCHAR(255) NULL;

-- Agregar una restricción a datos existentes (falla si hay violaciones)
ALTER TABLE unidades_sangre
  ADD CONSTRAINT chk_vencimiento CHECK (fecha_vencimiento >= fecha_extraccion);

-- Ver la estructura
DESCRIBE unidades_sangre;
SHOW CREATE TABLE unidades_sangre\G

Antes de un ALTER en producción, revisa el tamaño de la tabla, el tiempo de bloqueo y si existe una ventana de mantenimiento. En MySQL 8 muchas operaciones son online, pero no todas.
