Un respaldo no probado no es un respaldo

Programar mysqldump y no volver a mirarlo es una falsa sensación de seguridad. El respaldo existe cuando puedes restaurarlo y demostrar que los datos están completos. La prueba de restauración es parte del procedimiento, no un extra.

Completo, incremental y binlog

TipoQué guardaCuándo usarlo
CompletoToda la baseBase diaria; punto de partida de la restauración
IncrementalSolo cambios desde el último respaldoCada 15 minutos, para reducir RPO
BinlogHistorial de cambios del servidorRecuperación punto en el tiempo (PITR)

Respaldo lógico con mysqldump

mysqldump \
  --host=127.0.0.1 \
  --user=dba_sangre \
  --password \
  --single-transaction \
  --routines \
  --triggers \
  --events \
  --set-gtid-purged=OFF \
  --databases banco_sangre \
  > /respaldo/banco_sangre_completo_$(date +%Y%m%d_%H%M).sql
  • --single-transaction: consistencia sin bloquear la operación (InnoDB).
  • --routines, --triggers, --events: incluye procedimientos, triggers y eventos.
  • --databases: guarda el CREATE DATABASE y el USE.

Comprime y firma el resultado. Un archivo de respaldo sin checksum no permite saber si se corrompió en el camino.

gzip -c /respaldo/banco_sangre_completo_*.sql | sha256sum > respaldo.sha256
ls -lh /respaldo/

Binlog y recuperación punto en el tiempo

SHOW VARIABLES WHERE Variable_name IN (
  'log_bin', 'binlog_format', 'binlog_expire_logs_seconds', 'server_id'
);

SHOW BINARY LOGS;
SHOW MASTER STATUS;  -- en MySQL 8.4+ se usa SHOW BINARY LOG STATUS

Para restaurar hasta un punto exacto, se aplica el respaldo completo y después los binlogs hasta el minuto anterior al incidente:

mysqlbinlog --start-datetime="2026-11-01 00:00:00" \
            --stop-datetime="2026-11-01 12:00:00" \
  /respaldo/binlog/mysql-bin.000001 \
  | mysql --user=dba_sangre --password banco_sangre

Simulación de pérdida y restauración

-- 1. Estado previo
SELECT COUNT(*) AS unidades_antes FROM unidades_sangre;

-- 2. Simular el error dentro de una transacción
START TRANSACTION;
DELETE FROM despacho_detalle WHERE id_despacho = 2;
DELETE FROM unidades_sangre WHERE id_unidad IN (3, 12);
SELECT COUNT(*) AS unidades_despues FROM unidades_sangre;
ROLLBACK;  -- en el simulacro, no se pierde nada

En un incidente real no haces ROLLBACK: restauras el respaldo completo y aplicas binlog hasta antes del borrado. Después validas:

SELECT COUNT(*) AS unidades_restauradas FROM unidades_sangre;
SELECT COUNT(*) AS despachos_restaurados FROM despachos;

-- ¿Hay huérfanos?
SELECT dd.id_despacho, dd.id_unidad
FROM despacho_detalle dd
LEFT JOIN despachos d ON d.id_despacho = dd.id_despacho
LEFT JOIN unidades_sangre u ON u.id_unidad = dd.id_unidad
WHERE d.id_despacho IS NULL OR u.id_unidad IS NULL;

RTO, RPO y la prueba real

El banco de sangre define RTO de 30 minutos y RPO de 15 minutos. Eso obliga a:

  • Respaldo completo diario a las 02:00.
  • Binlog copiado cada 15 minutos.
  • Copia externa cifrada (off-site).
  • Restauración probada cada trimestre, midiendo el tiempo real.
  • Retención: 30 días completos, 12 meses mensuales, 7 años de auditoría.

Si la restauración tarda 50 minutos, tu RTO real es 50 minutos, no 30. La prueba es la que manda.

Caso banco de sangre

El script 04_unidad4_respaldo_recuperacion.sql documenta el procedimiento, la simulación y el checklist. El script 04_respaldo_incremental.sh automatiza el respaldo completo y la copia del binlog. Ambos son parte del entregable de la unidad 4.

Checklist de verificación

  • El respaldo termina sin errores y pesa un tamaño razonable.
  • El archivo contiene CREATE TABLE y datos.
  • El checksum coincide con el del servidor de respaldo.
  • La restauración en un servidor limpio reproduce los conteos.
  • Los triggers y eventos existen después de restaurar.
  • El binlog permite recuperar hasta el minuto del incidente.
  • El tiempo real de restauración es ≤ RTO.
  • El punto de recuperación es ≤ RPO.

Errores comunes

  • Respaldar sin --single-transaction y obtener una copia inconsistente.
  • Guardar el respaldo en el mismo disco del servidor.
  • No incluir triggers, eventos o rutinas.
  • No probar la restauración nunca.
  • Confundir el respaldo con la replicación: la réplica no protege de un DROP TABLE.
  • No cifrar la copia externa con datos de pacientes.
