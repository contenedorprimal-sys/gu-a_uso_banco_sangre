Guardar lógica en el servidor

Una consulta se escribe y se olvida. Una rutina se guarda con nombre y se ejecuta cuando hace falta. En MySQL las más comunes son los procedimientos almacenados (PROCEDURE), los disparadores (TRIGGER) y los eventos (EVENT).

DELIMITER //

CREATE PROCEDURE sp_resumen_inventario(IN p_componente VARCHAR(30))
BEGIN
  SELECT
    tipo_componente,
    estado,
    COUNT(*) AS unidades,
    SUM(volumen_ml) AS volumen_ml
  FROM unidades_sangre
  WHERE tipo_componente = p_componente
  GROUP BY tipo_componente, estado
  ORDER BY estado;
END //

DELIMITER ;

CALL sp_resumen_inventario('globulos_rojos');

DELIMITER //

CREATE PROCEDURE sp_total_disponible(OUT p_total INT)
BEGIN
  SELECT COUNT(*) INTO p_total
  FROM unidades_sangre
  WHERE estado = 'disponible';
END //

Variables, IF y transacciones dentro de una rutina

DELIMITER //

CREATE PROCEDURE sp_despachar_unidad(
  IN p_id_unidad INT,
  IN p_id_despacho INT,
  OUT p_resultado VARCHAR(120)
)
BEGIN
  DECLARE v_estado VARCHAR(20);

  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    ROLLBACK;
    SET p_resultado = 'error: transacción revertida';
  END;

  START TRANSACTION;

  SELECT estado INTO v_estado
  FROM unidades_sangre
  WHERE id_unidad = p_id_unidad
  FOR UPDATE;

  IF v_estado IS NULL THEN
    SET p_resultado = 'error: la unidad no existe';
    ROLLBACK;
  ELSEIF v_estado <> 'reservada' THEN
    SET p_resultado = CONCAT('error: estado no permitido (', v_estado, ')');
    ROLLBACK;
  ELSE
    INSERT INTO despacho_detalle (id_despacho, id_unidad)
    VALUES (p_id_despacho, p_id_unidad);

    UPDATE unidades_sangre
    SET estado = 'despachada'
    WHERE id_unidad = p_id_unidad;

    COMMIT;
    SET p_resultado = 'ok';
  END IF;
END //

DELIMITER ;

FOR UPDATE bloquea la fila mientras se decide. El EXIT HANDLER garantiza que un error no deje la transacción abierta. Una rutina que escribe debe tener una estrategia explícita de COMMIT y ROLLBACK.

Triggers: reaccionar a un cambio

Un trigger se ejecuta automáticamente ante un INSERT, UPDATE o DELETE. No se llama con CALL: se dispara con el cambio.

MomentoSirve paraEjemplo
BEFORE INSERTValidar o completar datosRechazar un volumen negativo.
AFTER INSERTAuditar o propagarRegistrar la entrada en el historial.
BEFORE UPDATEValidar el cambioImpedir cambiar una unidad despachada.
AFTER UPDATEGuardar el antes y el despuésAuditoría de estados.
BEFORE DELETEProteger o archivarImpedir borrar una unidad con despacho.
 
DELIMITER //

CREATE TRIGGER trg_unidades_auditoria
AFTER UPDATE ON unidades_sangre
FOR EACH ROW
BEGIN
  IF NOT (OLD.estado <=> NEW.estado) THEN
    INSERT INTO auditoria_unidades
      (id_unidad, accion, usuario, datos_anteriores, datos_nuevos)
    VALUES (
      OLD.id_unidad,
      'UPDATE',
      USER(),
      JSON_OBJECT('estado', OLD.estado, 'ubicacion', OLD.ubicacion),
      JSON_OBJECT('estado', NEW.estado, 'ubicacion', NEW.ubicacion)
    );
  END IF;
END //

DELIMITER ;

OLD tiene el valor anterior y NEW el nuevo. En un INSERT no existe OLD; en un DELETE no existe NEW. El operador <=> compara también NULL sin devolver NULL.

Triggers que se muerden la cola

Un trigger AFTER UPDATE que actualiza la misma tabla puede volver a dispararse. MySQL limita la recursión, pero el diseño sigue siendo frágil. Mantén los triggers cortos, sin llamadas externas y sin lógica de negocio pesada.

Eventos: tareas programadas

SHOW VARIABLES LIKE 'event_scheduler';

-- Requiere privilegio de administrador
SET GLOBAL event_scheduler = ON;

CREATE EVENT IF NOT EXISTS ev_marcar_vencidas
ON SCHEDULE EVERY 1 DAY
STARTS CURRENT_TIMESTAMP + INTERVAL 1 MINUTE
DO
  UPDATE unidades_sangre
  SET estado = 'vencida'
  WHERE estado = 'disponible'
    AND fecha_vencimiento < CURDATE();

El evento existe aunque el scheduler esté apagado; simplemente no corre. Antes de confiar en él, verifica event_scheduler = ON y deja evidencia de cada ejecución. Un UPDATE automático sin monitoreo es un incidente esperando su turno.

Caso banco de sangre

El proyecto usa un procedimiento para despachar, triggers para auditar cambios de estado y un evento para marcar vencimientos y guardar el Uptime. Cada mecanismo tiene una responsabilidad distinta: la aplicación no necesita recordar la auditoría ni el vencimiento.

Práctica

-- 1. Procedimiento que cuenta unidades por estado
DELIMITER //
CREATE PROCEDURE sp_conteo_por_estado()
BEGIN
  SELECT estado, COUNT(*) AS unidades
  FROM unidades_sangre
  GROUP BY estado
  ORDER BY unidades DESC;
END //
DELIMITER ;

CALL sp_conteo_por_estado();

-- 2. Ver los triggers y eventos existentes
SHOW TRIGGERS;
SHOW EVENTS;

-- 3. Apagar un evento sin borrarlo
ALTER EVENT ev_marcar_vencidas DISABLE;
ALTER EVENT ev_marcar_vencidas ENABLE;
