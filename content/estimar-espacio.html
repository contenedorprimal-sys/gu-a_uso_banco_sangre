Por qué estimar antes de crear

Quedarse sin disco en producción es uno de los incidentes más comunes y más evitables. La estimación no es un trámite: decide el hardware, el presupuesto y la estrategia de crecimiento.

  • Evita sorpresas costosas: un servidor que se llena un viernes a las 3 a.m.
  • Elige el hardware correcto: no compras el doble «por si acaso» ni la mitad «porque alcanza».
  • Planea finanzas: el almacenamiento crece y hay que presupuestarlo.

La fórmula de clase

1. bytes por fila = suma de bytes de cada columna

2. datos = bytes por fila × filas esperadas

3. índices = datos × 0.20 (rango razonable 10 %–30 %)

4. crecimiento = (datos + índices) × 1.20 a 1.30

Ejemplo resuelto: donantes

Tabla donantes con 8,000 filas nuevas al año:

nombre            VARCHAR(60)    60
apellido_paterno  VARCHAR(60)    60
apellido_materno  VARCHAR(60)    60
fecha_nacimiento  DATE            3
sexo              ENUM            1
tipo_sangre       ENUM            1
factor_rh         ENUM            1
telefono          VARCHAR(20)    20
correo            VARCHAR(120)  120
direccion         VARCHAR(160)  160
fecha_registro    DATETIME        8
activo            TINYINT         1
                                ----
bytes por fila                 495

datos       = 495 × 8,000        = 3,960,000 bytes  (~3.78 MB)
índices 20% = 3,960,000 × 0.20   =   792,000 bytes
subtotal                        = 4,752,000 bytes
margen 30%  = 4,752,000 × 1.30   = 6,177,600 bytes  (~5.89 MB)

La cifra parece pequeña porque la tabla es pequeña. El problema aparece en movimientos_inventario: 120,000 filas al año con textos de 80 y 255 bytes.

Estimación del proyecto completo

El script 02_unidad2_espacio_particiones_eventos.sql calcula cinco tablas con variables. Puedes cambiar los supuestos sin reescribir la fórmula:

SET @filas_movimientos = 120000;
SET @bytes_movimientos = 8 + 4 + 2 + 8 + 80 + 255;

SELECT
  @filas_movimientos AS filas,
  @bytes_movimientos AS bytes_fila,
  ROUND(@filas_movimientos * @bytes_movimientos / 1024 / 1024, 2) AS datos_mb,
  ROUND(@filas_movimientos * @bytes_movimientos * 1.20 / 1024 / 1024, 2) AS con_indices_mb,
  ROUND(@filas_movimientos * @bytes_movimientos * 1.20 * 1.30 / 1024 / 1024, 2) AS con_margen_mb;

Resultado aproximado: 40 MB de datos, 48 MB con índices y 62 MB con margen para un año. Con diez años de historial, la tabla de movimientos pasa de 400 MB solo en datos. Ahí es donde tiene sentido particionar y archivar.

No estimes solo lo actual

El error más común es calcular con las filas de hoy. Un sistema que crece 5 % semanal duplica su tamaño en pocos meses. Usa históricos o proyecciones y revisa la estimación cada trimestre.

La verdad del servidor: information_schema

La estimación es una hipótesis; information_schema.TABLES es la medición. Esta consulta es la que más se repite en el examen y en el trabajo diario:

SELECT
  table_name AS tabla,
  table_rows AS filas_estimadas,
  ROUND(data_length / 1024 / 1024, 3)  AS datos_mb,
  ROUND(index_length / 1024 / 1024, 3) AS indices_mb,
  ROUND((data_length + index_length) / 1024 / 1024, 3) AS total_mb,
  ROUND(index_length / NULLIF(data_length + index_length, 0) * 100, 2) AS pct_indices
FROM information_schema.TABLES
WHERE table_schema = 'banco_sangre'
  AND table_type = 'BASE TABLE'
ORDER BY (data_length + index_length) DESC;

Ojo: table_rows es una estimación del motor, no un COUNT(*). Para el tamaño exacto de una tabla usa COUNT(*); para el espacio, esta vista es la referencia.

Define alertas, por ejemplo al 80 % de disco. Y mira la tendencia: un disco al 60 % que crece 5 % por semana es más urgente que uno al 75 % estable.

De la estimación a las estructuras

La jerarquía lógica clásica es tablespace → segmento → extensión → bloque. Los segmentos pueden ser de datos, de índice, temporales o de undo. Físicamente viven en archivos de datos, de control y de redo log.

  • Autoextend: deja que el archivo crezca solo. Cómodo, pero sin límite puede llenar el disco.
  • Separar datos y logs: en discos distintos reduce contención de E/S.
  • Separar tablas muy usadas: reparte la carga, aunque en SSD el beneficio es menor.
