Lo que no se mide no se administra

Un DBA no debería enterarse de que el disco está lleno porque falló una escritura. El monitoreo proactivo mira tendencias, define umbrales y alerta antes del incidente. Las tres fuentes principales en MySQL son performance_schema, information_schema y las tablas propias de bitácora.

Estado general del servidor

SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.global_status
WHERE VARIABLE_NAME IN (
  'Uptime',
  'Threads_connected',
  'Threads_running',
  'Questions',
  'Slow_queries',
  'Aborted_connects',
  'Innodb_buffer_pool_read_requests',
  'Innodb_buffer_pool_reads'
);
VariableQué te dice
UptimeSegundos desde el último arranque; un valor bajo inesperado sugiere reinicio
Threads_connectedConexiones abiertas
Threads_runningConsultas ejecutándose ahora
Slow_queriesConsultas que superaron long_query_time
Aborted_connectsConexiones rechazadas: credenciales, red o límite

Consultas activas

SELECT id, user, host, db, command, time, state, LEFT(info, 120) AS consulta
FROM performance_schema.processlist
WHERE command <> 'Sleep'
ORDER BY time DESC;

En MySQL 8.0.22+ usa performance_schema.processlist; la versión de information_schema está deprecada. Una consulta con time alto y estado Locked o Waiting for ... puede estar bloqueando a otras. No la mates sin entender qué hace: quizá sea una transacción importante.

Consultas más costosas

SELECT
  DIGEST_TEXT,
  COUNT_STAR AS ejecuciones,
  ROUND(SUM_TIMER_WAIT / 1000000000000, 3) AS segundos_totales,
  ROUND(AVG_TIMER_WAIT / 1000000000, 3) AS ms_promedio
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'banco_sangre'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

Los timers de performance_schema están en picosegundos: divide entre 1e12 para segundos y entre 1e9 para milisegundos. Esta vista agrupa consultas equivalentes y muestra dónde se va el tiempo. Es el punto de partida de la unidad 5: primero se mide, después se indexa.

Eventos programados

SELECT event_schema, event_name, status,
       interval_value, interval_field,
       last_executed, last_altered
FROM information_schema.events
WHERE event_schema = 'banco_sangre';

last_executed es la evidencia. Un evento con estado ENABLED pero sin ejecución reciente está fallando en silencio.

Espacio y crecimiento

SELECT
  table_name,
  table_rows,
  ROUND((data_length + index_length) / 1024 / 1024, 2) AS total_mb,
  ROUND(index_length / NULLIF(data_length + index_length, 0) * 100, 2) AS pct_indices
FROM information_schema.tables
WHERE table_schema = 'banco_sangre'
ORDER BY (data_length + index_length) DESC;

Complementa con df -h en el sistema operativo. MySQL te dice cuánto ocupan sus tablas; el sistema operativo te dice cuánto queda en el disco.

Auditoría: la evidencia del cambio

El estado actual responde «¿dónde está la unidad?». La auditoría responde «¿quién la cambió y cuándo?». Para operaciones sensibles, la segunda pregunta es obligatoria.

CREATE TRIGGER trg_unidades_after_update
AFTER UPDATE ON unidades_sangre
FOR EACH ROW
BEGIN
  INSERT INTO auditoria_unidades
    (id_unidad, accion, usuario, datos_anteriores, datos_nuevos)
  VALUES (
    NEW.id_unidad,
    'UPDATE',
    CURRENT_USER(),
    JSON_OBJECT('estado', OLD.estado, 'ubicacion', OLD.ubicacion),
    JSON_OBJECT('estado', NEW.estado, 'ubicacion', NEW.ubicacion)
  );
END;

Un trigger no reemplaza una política de auditoría, pero garantiza que el registro ocurra aunque la aplicación lo olvide. El proyecto crea tres: AFTER INSERT, AFTER UPDATE y AFTER DELETE.

Cuidado con el costo

Cada trigger agrega trabajo a la escritura. Auditar todo puede ser caro; audita lo sensible. En este caso, el cambio de estado de una unidad es exactamente lo que hay que vigilar.

Seguridad y mínimo privilegio

La auditoría se complementa con roles: laboratorio no borra, recepción no ve datos personales, auditoría no escribe. Si una cuenta comprometida tiene ALL PRIVILEGES, la auditoría sirve para saber qué pasó, no para evitarlo.

SHOW GRANTS FOR 'lab_user'@'localhost';
SELECT user, host FROM mysql.user ORDER BY user;
SELECT * FROM auditoria_unidades ORDER BY id_auditoria DESC LIMIT 10;

Monitoreo de disponibilidad

La tabla bitacora_disponibilidad guarda un snapshot de Uptime cada hora. Si aparece un hueco mayor a una hora o el Uptime retrocede, hubo un reinicio o una caída.

SELECT
  fecha_registro,
  uptime_seg,
  TIMESTAMPDIFF(MINUTE,
    LAG(fecha_registro) OVER (ORDER BY fecha_registro),
    fecha_registro) AS minutos_desde_anterior
FROM bitacora_disponibilidad
ORDER BY fecha_registro DESC
LIMIT 20;

Caso banco de sangre

La operación sensible no es «leer una unidad»: es cambiarla de disponible a despachada, vencida o descartada. Ese cambio mueve inventario real y afecta a pacientes. Por eso tiene trigger, rol restringido y consulta de auditoría en la demo.

Errores comunes

  • Mirar un valor aislado en vez de la tendencia.
  • No revisar los eventos: se cree que están corriendo y no.
  • Auditar sin proteger la tabla de auditoría.
  • Dar privilegios de más «para que funcione».
  • No probar que la alerta realmente llega a alguien.
