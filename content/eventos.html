Tareas que no deberían depender de la memoria

Un respaldo olvidado, un log que crece sin control, unidades vencidas que siguen marcadas como disponibles: son incidentes evitables. El Event Scheduler de MySQL ejecuta SQL en un horario definido, dentro del servidor, sin depender de un cron externo.

No reemplaza al DBA: lo libera de lo repetitivo para que se ocupe de lo que requiere criterio.

Primero, encender el programador

SET GLOBAL event_scheduler = ON;
SHOW VARIABLES LIKE 'event_scheduler';

Si el valor es OFF, el evento existe pero nunca corre. Este es el primer error de examen: crear el evento y no encender el scheduler.

Crear un evento

CREATE EVENT ev_marcar_vencidas
ON SCHEDULE EVERY 1 DAY
STARTS (TIMESTAMP(CURRENT_DATE) + INTERVAL 1 DAY + INTERVAL 3 HOUR)
DO
  UPDATE unidades_sangre
  SET estado = 'vencida'
  WHERE estado = 'disponible'
    AND fecha_vencimiento < CURRENT_DATE;

Partes de la sintaxis:

ParteQué hace
ON SCHEDULE EVERY 1 DAYFrecuencia
STARTS ...Primera ejecución
DO ...La sentencia o bloque que ejecuta
ENABLE / DISABLEActivar o pausar sin borrar

Varios eventos del proyecto

-- Registrar el movimiento de vencimiento una sola vez por unidad
CREATE EVENT ev_registrar_vencimientos
ON SCHEDULE EVERY 1 DAY
STARTS (TIMESTAMP(CURRENT_DATE) + INTERVAL 1 DAY + INTERVAL 4 HOUR)
DO
  INSERT INTO movimientos_inventario (id_unidad, tipo_movimiento, usuario, motivo)
  SELECT u.id_unidad, 'vencimiento', 'event_scheduler', 'Marcado automático por fecha'
  FROM unidades_sangre u
  WHERE u.estado = 'vencida'
    AND NOT EXISTS (
      SELECT 1 FROM movimientos_inventario m
      WHERE m.id_unidad = u.id_unidad
        AND m.tipo_movimiento = 'vencimiento'
    );

-- Guardar Uptime cada hora
CREATE EVENT ev_bitacora_uptime
ON SCHEDULE EVERY 1 HOUR
STARTS CURRENT_TIMESTAMP
DO
  INSERT INTO bitacora_disponibilidad (fecha_registro, uptime_seg)
  SELECT NOW(), VARIABLE_VALUE
  FROM performance_schema.global_status
  WHERE VARIABLE_NAME = 'Uptime';

-- Purgar auditoría vieja cada mes
CREATE EVENT ev_purgar_auditoria
ON SCHEDULE EVERY 1 MONTH
STARTS (TIMESTAMP(CURRENT_DATE) + INTERVAL 1 MONTH)
DO
  DELETE FROM auditoria_unidades
  WHERE fecha < NOW() - INTERVAL 12 MONTH;

Idempotencia

Un evento que se ejecuta cada día debe poder correr dos veces sin duplicar datos. Por eso ev_registrar_vencimientos usa NOT EXISTS: si ya hay un movimiento de vencimiento para esa unidad, no inserta otro.

Verificar y controlar

SHOW EVENTS FROM banco_sangre;

SELECT event_name, status, interval_value, interval_field,
       last_executed, last_altered
FROM information_schema.events
WHERE event_schema = 'banco_sangre';

-- Pausar sin borrar
ALTER EVENT ev_marcar_vencidas DISABLE;
ALTER EVENT ev_marcar_vencidas ENABLE;

-- Borrar definitivamente
DROP EVENT IF EXISTS ev_marcar_vencidas;

last_executed es la evidencia de que el evento corrió. Si está en NULL o muy atrasado, algo pasa.

Beneficios y riesgos

Beneficios

  • Consistencia: siempre se ejecuta igual
  • Tiempo liberado para tareas de criterio
  • Menos dependencia de una persona

Riesgos

  • Un DELETE silencioso mal escrito
  • Un evento que falla y nadie revisa
  • Dos eventos que se pisan
  • Automatizar una tarea que requería aprobación humana

Mitigación: revisar SHOW EVENTS, registrar el resultado en una tabla de bitácora, alertar si last_executed no avanza y probar el evento en un entorno de pruebas antes de producción.

Caso banco de sangre

El evento de vencimiento evita que una unidad caducada siga apareciendo como disponible. El de Uptime alimenta la bitácora de disponibilidad de la unidad 2. El de purga mantiene la auditoría manejable sin borrar evidencia reciente.

Lo que se pregunta en el examen

  • Crear la tabla monitoreo_disponibilidad y el evento ev_monitoreo_uptime que inserte Uptime cada hora.
  • Explicar la diferencia entre ENABLE, DISABLE y DROP.
  • Justificar el beneficio y el riesgo de automatizar sin supervisión.
  • Verificar con SHOW EVENTS que el evento quedó creado.
