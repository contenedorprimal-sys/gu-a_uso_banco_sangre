El orden correcto para afinar

  1. Memoria: ¿el buffer pool está bien dimensionado?
  2. Consultas: ¿cuáles son las más costosas y por qué?
  3. Índices: ¿el plan usa el índice correcto?
  4. Esquema: ¿los tipos y el modelo acompañan?
  5. Hardware: solo después de agotar lo anterior.

Empezar por comprar más RAM sin mirar las consultas es caro y a veces inútil.

Tres parámetros que importan

1. innodb_buffer_pool_size

Memoria que InnoDB dedica a cachear páginas de datos e índices. En un servidor dedicado, 50–70 % de la RAM. Es la mejora más grande y más barata antes de tocar consultas.

SELECT @@innodb_buffer_pool_size AS bytes,
       ROUND(@@innodb_buffer_pool_size / 1024 / 1024 / 1024, 2) AS gb;

-- Tasa de aciertos del buffer pool
SELECT
  ROUND(
    100 - (SELECT VARIABLE_VALUE FROM performance_schema.global_status
           WHERE VARIABLE_NAME = 'Innodb_buffer_pool_reads') /
    (SELECT VARIABLE_VALUE FROM performance_schema.global_status
     WHERE VARIABLE_NAME = 'Innodb_buffer_pool_read_requests') * 100,
    2
  ) AS hit_rate_pct;

2. innodb_log_file_size

Tamaño de los redo logs. Más grande = menos checkpoints y mejor escritura sostenida; más pequeño = recuperación más rápida tras una caída. Es un balance, no un número mágico.

SELECT @@innodb_log_file_size AS bytes,
       ROUND(@@innodb_log_file_size / 1024 / 1024, 2) AS mb;

3. max_connections

Subirlo sin memoria disponible solo mueve el problema: cada conexión consume buffers privados. Revisa también thread_cache_size y si la aplicación abre y cierra conexiones sin un pool.

SELECT @@max_connections AS max_conexiones,
       @@thread_cache_size AS thread_cache,
       (SELECT VARIABLE_VALUE FROM performance_schema.global_status
        WHERE VARIABLE_NAME = 'Threads_connected') AS conectadas_ahora;

La consulta crítica del proyecto

SELECT id_unidad, codigo_barras, tipo_componente, fecha_vencimiento
FROM unidades_sangre
WHERE estado = 'disponible'
  AND grupo_abo = 'O'
  AND factor_rh = '+'
ORDER BY fecha_vencimiento ASC;

Es la consulta del mostrador: «¿qué unidades O+ puedo despachar y cuál vence primero?». Se ejecuta muchas veces al día y debe ser instantánea.

Medir antes

EXPLAIN
SELECT id_unidad, codigo_barras, tipo_componente, fecha_vencimiento
FROM unidades_sangre
WHERE estado = 'disponible'
  AND grupo_abo = 'O'
  AND factor_rh = '+'
ORDER BY fecha_vencimiento ASC;

Si type = ALL, key = NULL o Extra = Using filesort, hay margen de mejora. Anota el plan y el tiempo; sin línea base no puedes demostrar nada.

Crear el índice justificado

CREATE INDEX idx_unidades_o_positivo
  ON unidades_sangre (grupo_abo, factor_rh, estado, fecha_vencimiento);

El orden sigue la consulta: igualdad (grupo_abo, factor_rh, estado) y después orden (fecha_vencimiento). Así MySQL puede recorrer el índice en el orden pedido y evitar el filesort.

Medir después

EXPLAIN
SELECT id_unidad, codigo_barras, tipo_componente, fecha_vencimiento
FROM unidades_sangre
WHERE estado = 'disponible'
  AND grupo_abo = 'O'
  AND factor_rh = '+'
ORDER BY fecha_vencimiento ASC;

-- Plan y tiempo real
EXPLAIN ANALYZE
SELECT id_unidad, codigo_barras, tipo_componente, fecha_vencimiento
FROM unidades_sangre
WHERE estado = 'disponible'
  AND grupo_abo = 'O'
  AND factor_rh = '+'
ORDER BY fecha_vencimiento ASC;

Cronómetro portable

-- MySQL 8.0 tiene SHOW PROFILES, pero está deprecado y en 8.4 ya no existe.
-- Mide con NOW(6) o usa EXPLAIN ANALYZE.
SET @inicio = NOW(6);
SELECT COUNT(*) INTO @total
FROM unidades_sangre
WHERE estado = 'disponible' AND grupo_abo = 'O' AND factor_rh = '+';
SET @fin = NOW(6);
SELECT @total AS filas,
       TIMESTAMPDIFF(MICROSECOND, @inicio, @fin) / 1000 AS ms;

Con 14 filas, el optimizador puede ignorar el índice y hacer table scan de todos modos. La mejora real se demuestra con un volumen representativo o con EXPLAIN ANALYZE mostrando menos filas examinadas.

No midas una vez

La primera ejecución incluye lectura de disco y calentamiento de caché. Ejecuta varias veces y compara promedios. Y no afines en producción sin una ventana y un plan de reversión.

Caso banco de sangre

El script 05_unidad5_afinacion.sql mide antes, crea el índice, mide después y documenta los parámetros. Es el entregable de la unidad 5: revisar tres parámetros, justificar un índice con EXPLAIN y comparar el tiempo de una consulta crítica.

Errores comunes

  • Crear índices sin medir y sin revisar el plan.
  • Indexar todas las columnas del WHERE sin importar el orden.
  • Subir max_connections sin memoria.
  • Comparar tiempos con la caché fría contra la caché caliente.
  • Olvidar ANALYZE TABLE después de cambios masivos.
  • Afinar una consulta que casi no se ejecuta mientras la crítica sigue lenta.
