Qué es realmente un índice

Un índice es una estructura auxiliar (normalmente un árbol B+) que mantiene una columna o varias ordenadas, con punteros a las filas. Sin índice, MySQL lee la tabla completa para encontrar una fila: un full table scan. Con índice, salta casi directamente a las filas que cumplen la condición.

La analogía del libro sirve: el índice del final no cambia el contenido, pero evita leer las 400 páginas para encontrar «failover».

Cuándo ayuda y cuándo estorba

Ayuda

  • Columnas usadas en WHERE
  • Columnas de JOIN
  • Columnas de ORDER BY
  • Columnas con muchos valores distintos
  • Búsquedas por rango de fechas

Estorba

  • Columnas con dos o tres valores (sexo, activo)
  • Tablas muy pequeñas
  • Demasiados índices: cada INSERT los actualiza
  • Consultas que ya leen casi toda la tabla

El orden de un índice compuesto importa

Un índice sobre (grupo_abo, factor_rh, estado, fecha_vencimiento) sirve para:

  • WHERE grupo_abo = 'O'
  • WHERE grupo_abo = 'O' AND factor_rh = '+'
  • WHERE grupo_abo = 'O' AND factor_rh = '+' AND estado = 'disponible'
  • …y además ordena por fecha_vencimiento dentro de esas igualdades.

No sirve para WHERE estado = 'disponible' sin las columnas anteriores: es como buscar en el índice de un libro por la tercera letra de la palabra.

Regla práctica

Ordena las columnas del índice así: primero las de igualdad, después las de rango, y al final las de orden. La consulta del mostrador usa igualdad en grupo, RH y estado, y orden por vencimiento; el índice sigue exactamente ese orden.

Crear el índice del proyecto

-- Consulta crítica: unidades O+ disponibles, la que vence primero
SELECT id_unidad, codigo_barras, tipo_componente, fecha_vencimiento
FROM unidades_sangre
WHERE estado = 'disponible'
  AND grupo_abo = 'O'
  AND factor_rh = '+'
ORDER BY fecha_vencimiento ASC;

-- Índice que cubre igualdad + orden
CREATE INDEX idx_unidades_o_positivo
  ON unidades_sangre (grupo_abo, factor_rh, estado, fecha_vencimiento);

En MySQL 8, EXPLAIN ANALYZE ejecuta la consulta y muestra el tiempo real por etapa. Es la diferencia entre «el plan dice» y «el plan hizo».

EXPLAIN ANALYZE
SELECT id_unidad, codigo_barras, tipo_componente, fecha_vencimiento
FROM unidades_sangre
WHERE estado = 'disponible'
  AND grupo_abo = 'O'
  AND factor_rh = '+'
ORDER BY fecha_vencimiento ASC;

Con 14 filas de demo la diferencia es de décimas de milisegundo. Con millones de unidades es la diferencia entre una pantalla instantánea y una que tarda segundos.

El costo de indexar

  • Ocupa espacio en disco y en memoria.
  • Hace más lento cada INSERT, UPDATE y DELETE, porque hay que mantener el árbol.
  • Puede confundir al optimizador si hay demasiados índices parecidos.
  • Un índice que nadie usa es deuda técnica: revísalo con performance_schema.
-- Índices de una tabla y su cardinalidad
SHOW INDEX FROM unidades_sangre;

-- Tamaño de los índices de la base
SELECT table_name,
       ROUND(index_length / 1024 / 1024, 2) AS indices_mb
FROM information_schema.TABLES
WHERE table_schema = 'banco_sangre'
ORDER BY index_length DESC;

Caso banco de sangre

El índice idx_unidades_o_positivo se crea en la unidad 5, después de medir. No se crea «porque suena bien»: se justifica con EXPLAIN antes y después, y se documenta el cambio en el README.

Errores frecuentes con índices

  • Indexar todo «por si acaso»: el rendimiento de escritura se degrada.
  • Crear un índice sobre una columna con LIKE '%texto%': el comodín al inicio impide usarlo.
  • Poner la columna de rango antes que las de igualdad en el índice compuesto.
  • No actualizar estadísticas después de cambios masivos: usa ANALYZE TABLE.
  • Confundir el índice con una copia de la tabla: no lo es.
