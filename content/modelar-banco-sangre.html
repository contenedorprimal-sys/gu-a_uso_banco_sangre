Del enunciado al modelo

El proyecto pide gestionar «el ciclo completo de la sangre»: registro de donantes, donaciones, unidades derivadas, pruebas de laboratorio, solicitudes de hospitales, despachos e inventario con trazabilidad. La tentación es hacer una tabla gigante. La pregunta correcta es: ¿qué hechos distintos ocurren en este proceso?

  1. Una persona se registra como donante.
  2. Esa persona dona un día concreto.
  3. De esa donación se derivan uno o varios componentes.
  4. A cada componente se le hacen pruebas.
  5. Un hospital solicita componentes.
  6. Se prepara un despacho y se entregan unidades concretas.
  7. Todo cambio de estado se registra para trazabilidad.

Cada hecho es una tabla. Las relaciones entre hechos son llaves foráneas.

  • Un donante puede tener muchas donaciones; una donación pertenece a un donante.
  • Una donación puede producir varias unidades; una unidad pertenece a una donación.
  • Una unidad puede tener muchas pruebas; una prueba pertenece a una unidad.
  • Una solicitud tiene varios detalles; cada detalle es un componente pedido.
  • Un despacho puede incluir varias unidades; una unidad se despacha una sola vez.

Cinco decisiones de diseño

1. Donación y unidad no son la misma tabla

Una donación de sangre total puede separarse en glóbulos rojos, plasma y plaquetas. Cada componente tiene volumen, vencimiento y estado propios. Si todo estuviera en una tabla, no podrías despachar el plasma sin «despachar» también los glóbulos rojos.

2. El estado vive en la unidad, no en el donante

El donante está sano; la unidad puede estar disponible, reservada, despachada, vencida o descartada. Son cosas distintas.

3. La trazabilidad es una tabla, no una columna

Guardar solo el estado actual responde «¿dónde está?», pero no «¿quién la movió y cuándo?». movimientos_inventario y auditoria_unidades responden la segunda pregunta.

4. Datos personales separados de datos clínicos

donantes contiene contacto e identificación. Las pruebas y unidades no necesitan el correo del donante. Esa separación permite dar acceso a recepción sin exponer datos personales.

5. La tabla particionada pierde la FK

movimientos_inventario crece sin parar y se particiona por año. MySQL exige que la columna de partición esté en la PK y prohíbe FKs en tablas particionadas. La integridad se mantiene con la aplicación y la auditoría; es un trade-off documentado.

Normalización sin dogma

La tercera forma normal (3FN) evita dependencias transitivas: cada dato no clave depende de la clave, de toda la clave y nada más que de la clave. En el caso:

  • El nombre del hospital no se repite en cada solicitud: se guarda una vez en hospitales.
  • El tipo de componente no se repite como texto libre: se usa un ENUM controlado.
  • El detalle de una solicitud no repite la fecha de la solicitud: se obtiene con un JOIN.

Normalizar no significa nunca duplicar. En analítica a veces se desnormaliza a propósito para evitar JOINs costosos. En un sistema transaccional como este, la integridad pesa más.

El esquema completo

El script 00_esquema.sql crea 12 tablas, una vista y 19 índices. Las tablas centrales son:

CREATE TABLE unidades_sangre (
  id_unidad         INT AUTO_INCREMENT PRIMARY KEY,
  id_donacion       INT NOT NULL,
  codigo_barras     VARCHAR(40) NOT NULL UNIQUE,
  tipo_componente   ENUM('sangre_total','globulos_rojos','plasma','plaquetas','crioprecipitado') NOT NULL,
  grupo_abo         ENUM('A','B','AB','O') NOT NULL,
  factor_rh         ENUM('+','-') NOT NULL,
  volumen_ml        INT NOT NULL,
  fecha_extraccion  DATE NOT NULL,
  fecha_vencimiento DATE NOT NULL,
  estado            ENUM('disponible','reservada','despachada','vencida','descartada')
                    NOT NULL DEFAULT 'disponible',
  ubicacion         VARCHAR(40),
  CONSTRAINT fk_unidad_donacion
    FOREIGN KEY (id_donacion) REFERENCES donaciones (id_donacion)
    ON UPDATE CASCADE ON DELETE CASCADE,
  CONSTRAINT chk_unidad_volumen CHECK (volumen_ml > 0),
  CONSTRAINT chk_unidad_fechas CHECK (fecha_vencimiento >= fecha_extraccion)
) ENGINE=InnoDB;
CREATE TABLE despacho_detalle (
  id_despacho INT NOT NULL,
  id_unidad   INT NOT NULL,
  PRIMARY KEY (id_despacho, id_unidad),
  CONSTRAINT fk_despacho_detalle_despacho
    FOREIGN KEY (id_despacho) REFERENCES despachos (id_despacho)
    ON UPDATE CASCADE ON DELETE CASCADE,
  CONSTRAINT fk_despacho_detalle_unidad
    FOREIGN KEY (id_unidad) REFERENCES unidades_sangre (id_unidad)
    ON UPDATE CASCADE ON DELETE RESTRICT
) ENGINE=InnoDB;

La PK compuesta de despacho_detalle impide que la misma unidad se incluya dos veces en el mismo despacho. Es una regla de negocio expresada en el esquema.
