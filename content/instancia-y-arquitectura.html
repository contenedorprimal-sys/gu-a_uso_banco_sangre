Instancia frente a base de datos

La confusión más común al empezar: «el servidor» y «la base de datos» no son lo mismo.

Instancia

Procesos y memoria en ejecución. Es lo que administra: atiende conexiones, ejecuta consultas, escribe en disco.

Base de datos

Archivos físicos donde viven los datos. Persisten aunque la instancia se detenga.

Por eso reiniciar MySQL no borra nada: la instancia se apaga y vuelve a leer los archivos. Y por eso una copia de los archivos con la instancia encendida puede ser inconsistente.

Tres capas: procesos, memoria y archivos

  • Procesos en primer plano: atienden la conexión del cliente, reciben SQL y devuelven resultados.
  • Procesos en segundo plano: escriben cambios, gestionan checkpoints, limpian memoria y garantizan recuperación.
  • Archivos en disco: datos, metadatos, logs y configuración.

En MySQL, la capa de almacenamiento de InnoDB es la que da transacciones ACID, bloqueos por fila y recuperación ante fallas. El query cache desapareció en MySQL 8; el caché real que importa es el buffer pool.

El buffer pool: la memoria que más se nota

InnoDB guarda en RAM las páginas de datos e índices que se leen o modifican. Si la página está en el buffer pool, la consulta no toca el disco. Si no está, hay que leerla y probablemente escribirla después.

-- Tamaño actual del buffer pool
SELECT @@innodb_buffer_pool_size AS bytes,
       ROUND(@@innodb_buffer_pool_size / 1024 / 1024 / 1024, 2) AS gb;

-- ¿Qué tan bien está funcionando el caché?
SELECT VARIABLE_NAME, VARIABLE_VALUE
FROM performance_schema.global_status
WHERE VARIABLE_NAME IN (
  'Innodb_buffer_pool_read_requests',
  'Innodb_buffer_pool_reads'
);

La proporción entre read_requests y reads te dice cuántas lecturas se resolvieron en memoria. Si reads crece demasiado, el buffer pool se queda corto o la consulta recorre demasiadas páginas.

Error común

Subir max_connections sin memoria. Cada conexión consume buffers privados; más conexiones con poca RAM solo cambian un cuello de botella por otro.

Redo log: la promesa de que no se pierde

Cuando confirmas una transacción con COMMIT, InnoDB escribe el cambio en el redo log antes de modificar la página definitiva en disco. Si el servidor se cae, al reiniciar se reproduce el log y el cambio confirmado sobrevive. Esa es la base de la durabilidad (la D de ACID).

-- Parámetros que conviene conocer antes de afinar
SELECT @@innodb_log_file_size AS redo_mb,
       @@innodb_flush_log_at_trx_commit AS flush_en_commit,
       @@innodb_buffer_pool_instances AS instancias;

innodb_flush_log_at_trx_commit = 1 es lo seguro para un banco de sangre: cada commit se sincroniza a disco. Bajarlo mejora el rendimiento y aumenta la ventana de pérdida.

Caso banco de sangre

La unidad GR-2026-0001 se marcó como despachada a las 09:20. El COMMIT llegó al redo log; el servidor se cayó un segundo después. Al reiniciar, la unidad sigue despachada y la auditoría conserva el cambio. Sin redo log, el sistema «olvidaría» un despacho real.

Práctica de dos minutos

SHOW VARIABLES LIKE 'datadir';
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW ENGINE INNODB STATUS\G

El último comando imprime mucho texto: busca la sección BUFFER POOL AND MEMORY y la sección TRANSACTIONS. Saber leer esas dos secciones vale más que memorizar decenas de parámetros.
