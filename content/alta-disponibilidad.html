Qué significa «alta disponibilidad»

No significa «nunca falla». Ningún sistema es perfecto. Significa diseñar para que, cuando algo falle, afecte lo menos posible. La disponibilidad se planea desde la arquitectura, no se agrega como parche después de un incidente.

Y no es lo mismo que tener respaldos: un respaldo protege los datos ante una pérdida; la alta disponibilidad protege el servicio en tiempo real.

Los nueves: de porcentaje a horas

DisponibilidadCaída al añoCaída al mes
99 % («two nines»)~3.65 días~7.3 horas
99.9 % («three nines»)~8.77 horas~43.8 minutos
99.99 % («four nines»)~52.6 minutos~4.4 minutos
99.999 % («five nines»)~5.26 minutos~26.3 segundos

Un año tiene 525,600 minutos. La fórmula es:

% disponibilidad = (minutos totales − minutos caídos) / minutos totales × 100

Ejemplo resuelto

Un sistema tuvo 2 horas con 15 minutos de inactividad: 135 minutos.

SELECT ROUND(((525600 - 135) / 525600) * 100, 4) AS disponibilidad;

Resultado: 99.9743 %. No llega a 99.99 % (que permite 52.6 minutos), así que se clasifica como 99.9 % («tres nueves»). Ojo: 135 minutos está muy por encima de los 52.6 minutos de four nines.

-- Con variables, como se pide en el examen
SET @total = 525600;
SET @caida = 135;
SELECT ROUND((@total - @caida) / @total * 100, 4) AS pct;

-- Otros escenarios
SELECT ROUND((525600 - 270) / 525600 * 100, 4) AS pct_4h30;  -- 99.9486
SELECT ROUND((525600 - 50)  / 525600 * 100, 4) AS pct_50min; -- 99.9905
SELECT ROUND((525600 - 480) / 525600 * 100, 4) AS pct_8h;    -- 99.9087

RTO y RPO: los dos números que definen la arquitectura

RTO

Recovery Time Objective. Cuánto tiempo, como máximo, se tolera que el sistema esté fuera de servicio antes de que el negocio se vea afectado.

RPO

Recovery Point Objective. Cuánta información se tolera perder, medido en tiempo: «no más de 15 minutos de datos».

Un RTO y un RPO muy exigentes requieren clustering y replicación. Objetivos más relajados pueden resolverse con buenos respaldos.

Ejemplo: banca en línea

El servidor cae a las 11:00 y el último respaldo completo fue a las 5:00.

  • RTO propuesto: 15–30 minutos. Cada minuto de caída cuesta dinero y confianza.
  • RPO implícito: 6 horas. Se pueden perder hasta seis horas de transacciones confirmadas.
  • Acción para reducir RPO: activar binlog y respaldos incrementales cada 15 minutos, además de una réplica.

Redundancia: eliminar el SPOF

Un SPOF (Single Point of Failure) es un componente cuya falla tumba todo el servicio. La solución es no depender de un solo componente para nada crítico.

TipoEjemplo
HardwareFuentes duplicadas, RAID, más de un servidor
DatosRespaldo o replicación en tiempo real
RedMás de una ruta entre aplicación y base

La redundancia cuesta: más servidores, más almacenamiento, más complejidad. El nivel se decide según qué tan crítico es el sistema. Un banco de sangre con cirugías en curso no es lo mismo que un blog personal.

RTO y RPO del banco de sangre

ObjetivoValorJustificación
Disponibilidad99.9 %~8.77 h de caída al año; suficiente para un hospital con ventanas de mantenimiento
RTO30 minHay cirugías y urgencias; no se puede esperar horas
RPO15 minSe tolera perder como máximo 15 minutos de capturas

Con esos objetivos, un respaldo diario no alcanza: se necesita binlog cada 15 minutos y, para el RTO, una réplica o clúster con failover.

Entregable de la unidad 2

Documentar un escenario de RTO/RPO propio, con justificación de negocio y una acción concreta para reducir el RPO. El README del proyecto lo hace para el banco de sangre: RTO 30 min, RPO 15 min, binlog + incremental.

Errores comunes

  • No definir RTO/RPO explícitamente: sin objetivos no se puede saber si la arquitectura cumple.
  • Implementar clustering en un sistema que no lo necesita: complejidad sin beneficio.
  • Ignorar el SPOF fuera de la base de datos: un clúster robusto detrás de un solo servidor web sigue cayéndose.
  • Confundir respaldo con alta disponibilidad.
  • Calcular los nueves con el mes en vez del año (o mezclar unidades).
