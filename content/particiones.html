Fragmentar no es lo mismo que repartir servidores

Fragmentación es una decisión lógica: cómo dividir una tabla grande en partes manejables. Sharding es una decisión física: en qué servidor vive cada parte. MySQL implementa la fragmentación horizontal de forma nativa con PARTITION BY; el sharding requiere arquitectura adicional.

Horizontal, vertical y mixta

  • Horizontal: divide por filas. Cada fragmento tiene las mismas columnas y un subconjunto de registros (por año, región, estado).
  • Vertical: divide por columnas. Cada fragmento tiene todas las filas y solo algunas columnas (contacto frecuente vs. historial raro).
  • Mixta: combina las dos. Más flexible, más difícil de mantener.

MySQL particiona horizontalmente, no verticalmente. La fragmentación vertical se implementa separando tablas o usando vistas.

RANGE por año: el historial que no deja de crecer

CREATE TABLE movimientos_inventario (
  id_movimiento    BIGINT NOT NULL AUTO_INCREMENT,
  id_unidad        INT NOT NULL,
  tipo_movimiento  ENUM('entrada','reserva','liberacion','salida','descarte','vencimiento','ajuste') NOT NULL,
  fecha_movimiento DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  usuario          VARCHAR(80),
  motivo           VARCHAR(255),
  PRIMARY KEY (id_movimiento, fecha_movimiento)
) ENGINE=InnoDB
PARTITION BY RANGE (YEAR(fecha_movimiento)) (
  PARTITION p2024 VALUES LESS THAN (2025),
  PARTITION p2025 VALUES LESS THAN (2026),
  PARTITION p2026 VALUES LESS THAN (2027),
  PARTITION p2027 VALUES LESS THAN (2028),
  PARTITION pmax  VALUES LESS THAN MAXVALUE
);

La columna fecha_movimiento está en la PK. No es capricho: MySQL exige que toda clave única incluya la columna de partición. Y la tabla no tiene FOREIGN KEY, porque las tablas particionadas no las admiten.

-- Ver el reparto
SELECT partition_name, table_rows
FROM information_schema.PARTITIONS
WHERE table_schema = 'banco_sangre'
  AND table_name = 'movimientos_inventario'
ORDER BY partition_ordinal_position;

-- El optimizador solo toca la partición del año
EXPLAIN
SELECT COUNT(*) FROM movimientos_inventario
WHERE fecha_movimiento >= '2026-01-01'
  AND fecha_movimiento <  '2027-01-01';

LIST por categoría

CREATE TABLE solicitudes_list (
  id_solicitud     INT NOT NULL,
  id_hospital      INT NOT NULL,
  fecha_solicitud  DATETIME NOT NULL,
  prioridad        ENUM('urgente','programada') NOT NULL,
  estado           VARCHAR(10) NOT NULL,
  PRIMARY KEY (id_solicitud, estado)
) ENGINE=InnoDB
PARTITION BY LIST COLUMNS(estado) (
  PARTITION p_pendiente VALUES IN ('pendiente'),
  PARTITION p_parcial   VALUES IN ('parcial'),
  PARTITION p_surtida   VALUES IN ('surtida'),
  PARTITION p_cancelada VALUES IN ('cancelada')
);

Para texto se usa LIST COLUMNS, no LIST. Tampoco acepta ENUM: por eso estado es VARCHAR en esta copia. Si insertas un valor que no está en ninguna partición, el INSERT falla: la partición LIST es cerrada.

HASH para reparto uniforme

CREATE TABLE pruebas_hash (
  id_prueba    INT NOT NULL,
  id_unidad    INT NOT NULL,
  tipo_prueba  ENUM('VIH','HBV','HCV','sifilis','chagas','grupo_sanguineo','pruebas_cruzadas') NOT NULL,
  resultado    ENUM('negativo','positivo','pendiente') NOT NULL,
  fecha_prueba DATETIME NOT NULL,
  PRIMARY KEY (id_prueba, id_unidad)
) ENGINE=InnoDB
PARTITION BY HASH(id_unidad)
PARTITIONS 4;

HASH no tiene criterio de negocio visible: reparte por una función. Sirve para paralelizar y para equilibrar, no para «consultar solo el año 2026».

Las reglas que cuestan puntos

No las olvides

  • La columna de partición debe formar parte de la PRIMARY KEY.
  • Una tabla particionada no puede tener FOREIGN KEY.
  • Para VARCHAR usa LIST COLUMNS.
  • Las particiones son parte del diseño: se definen al crear la tabla, no se «activan» después.
  • No particiones por una columna que las consultas no filtran.

¿Cuándo vale la pena particionar?

  • La tabla es grande y crece de forma acumulativa (historial, bitácora, movimientos).
  • Las consultas filtran por la columna de partición (fecha, región, estado).
  • Necesitas archivar o borrar un año completo sin tocar el resto: ALTER TABLE ... DROP PARTITION es mucho más barato que un DELETE masivo.

Si la tabla es pequeña o las consultas no usan el criterio, particionar solo agrega complejidad.

Caso banco de sangre

movimientos_inventario es la tabla que más crece: cada entrada, reserva, salida, descarte y vencimiento deja una fila. Particionarla por año permite consultar «movimientos de 2026» sin leer 2024 ni 2025, y archivar un año completo cuando ya no se necesita en línea.

Errores comunes

  • Particionar una tabla con FK y descubrir el error a la mitad.
  • Usar LIST con texto en vez de LIST COLUMNS.
  • Elegir un criterio que no aparece en los WHERE.
  • Creer que la partición reemplaza un índice: no lo hace.
  • Confundir fragmentación lógica con sharding físico.
